      왼쪽에서 결제를 하나 고르세요

      판정 엔진이 관문을 하나씩 지나가며 무엇을 봤는지 여기에 적습니다.

      체험용 예시 결제입니다. 규칙 카드 번호와 판정, 근거 조문, 되묻기 질문은 실제 서비스의 규칙 카드(rules/cards)와 같습니다. 조문 원문은 발췌이며, 서비스에서는 국가법령정보센터에서 받아 시행일별로 저장한 원문을 보여 줍니다.

      3. 판정 구조와 설계 결정

      AI가 규칙을 만들고,
      규칙이 판정합니다

      판정 엔진 안에는 AI가 없습니다. 같은 결제는 언제 넣어도 같은 판정이 나와야 하기 때문입니다. AI는 판정 앞뒤에서 사람을 돕습니다.

      판정 경로

      같은 입력이면 항상 같은 결과
      1. 카드내역 읽기브라우저에서 KB·IBK 파일을 읽고 취소 건을 상계
      2. 가맹점 분류결제대행사 차단, 개인 사전, 전역 사전, 키워드 규칙 순서
      3. 규칙 엔진 6관문규칙 카드에 맞춰 가능, 불가, 확인 필요
      4. 근거 조문카드에 적힌 조문 번호로 시행일에 맞는 원문을 조회

      AI가 하는 일

      판정을 대신하지 않고 사람을 돕는 자리
      1. 판정 못 한 결제 모으기맞는 규칙 카드가 없으면 판정 대신 후보로 쌓음
      2. 규칙 카드 초안법령 원문을 검색해 조문 후보와 카드 초안을 만듦
      3. 사람이 승인팀과 세무 검수를 거쳐야 규칙이 됨
      4. 분류 보조 모델규칙으로 못 고른 가맹점의 카테고리 추천 (11월 연동)

      판정 경로에 LLM을 넣지 않았습니다

      판정 함수 안에는 LLM 호출도, 외부 API 호출도, 현재 시각 조회도 없습니다.

      이유 세금 판정에서 같은 결제가 날마다 다르게 나오면 그건 결함입니다. 분류가 틀려도 규칙이 맞지 않아 확인 필요로 떨어질 뿐, 틀린 판정이 나가지 않습니다.

      근거가 없으면 판정하지 않습니다

      가능과 불가에는 반드시 조문이 붙습니다. 맞는 규칙 카드가 없으면 근거 칸을 비우고 확인 필요로 둡니다.

      이유 그럴듯한 근거를 지어내는 것보다 질문 하나를 더 하는 편이 사용자에게 덜 위험합니다.

      조문 번호는 카드에 고정하고 원문은 DB에서

      규칙 카드에 조문 번호를 적어 두고, 원문은 법령 API로 받은 시행판에서 판정일에 맞는 것을 꺼냅니다.

      이유 모델이 조문 번호를 직접 만들면 없는 조문이 나옵니다. 지난해 결제에는 지난해 시행판을 인용해야 합니다.

      사람이 승인해야 규칙이 됩니다

      사용자의 답변은 그 사용자 한 명에게만 적용됩니다. 전체 사용자에게 적용되는 규칙 카드는 검수를 거쳐 저장소에 들어갑니다.

      이유 답변 하나가 틀리면 그 사람 판정 한 건이 틀리지만, 규칙이 틀리면 모든 사용자의 판정이 틀립니다.
